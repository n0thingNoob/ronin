# Hand-written kernels (phase 1 + 2)

This directory holds **hand-written** Tanto kernels and host programs. No DSL
codegen output lives here — that goes under `../codegen/` once phase 3 starts.

The point of this phase is to walk through the Tanto contract by hand so that
the DSL design (phase 3) is driven by lived experience of what hurts, not by
guesswork.

## What lives here

- `scalar_add/` — phase 1, single core, `C[i] = A[i] + 3.0`
- `two_core_add/` — phase 2 step 1, 2 cores, NOC L1→L1 mcast for inputs,
  `C = A + B` (SPMD-via-core_id)
- `three_core_add_relu/` — phase 2 step 2, 3 cores, full DAG (read / compute /
  forward / write), `C = relu(A + B)`, intermediate `T` never touches DRAM
  (SPMD-via-core_id)
- `mpmd_two_core_add/` — phase 2 step 3, **true MPMD**: same dataflow as
  `two_core_add` but with 6 separate kernel binaries (no `core_id`
  branching). Validates multi-Grid + multi-Kernel in one Program — the
  shape phase 3's DSL codegen will emit.
- `two_core_add_relu/` — superseded placeholder; original phase 2 plan that
  was replaced by the demos above (see ROADMAP decision log 2026-04-26)

## Layout convention (per operator)

Mirrors `algo/src/basic/`:

```
<op>/
├── device/
│   ├── tanto/    you write Tanto C++ here
│   └── metal/    generated by tanto frontend (front.sh)
├── host/         host program (Tanto host API)
└── test/         test driver: build inputs, call host, check answer
```

Build scripts live under `../../prj/handwritten/<op>/` (metal-side) and
`../../jitte/prj/handwritten/<op>/` (Jitte-side), again following the
`algo/` convention.
