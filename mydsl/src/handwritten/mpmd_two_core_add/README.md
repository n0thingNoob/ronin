# mpmd_two_core_add (phase 2 step 3 — true MPMD)

Same `C = A + B` over 4 tiles of bfloat16, same 2-core dataflow as
`two_core_add`. The difference is purely **how** the 2 roles are dispatched:

- `two_core_add`: one binary per kernel kind (reader/writer/math), branched
  by a `core_id` runtime arg. SPMD-style.
- `mpmd_two_core_add`: **6 separate kernel binaries**, no `core_id`. Each
  core gets its own reader, writer, math compiled from its own source file.
  Truly MPMD.

This validates that Tanto's host API supports multi-Grid + multi-Kernel in
one Program — the foundation phase 3's DSL needs to compile per-core
specialized kernels.

## Files

```
device/tanto/head_reader.cpp   no-op stub (head's NCRISC idle)
device/tanto/head_writer.cpp   DRAM read + NOC mcast pa, pb to tail
device/tanto/head_math.cpp     drain pa, pb (writer push without consumer)
device/tanto/tail_reader.cpp   credit-then-data handshake on pa, pb
device/tanto/tail_writer.cpp   drain pc to DRAM
device/tanto/tail_math.cpp     pc = pa + pb
device/metal/                  generated by ../../../prj/handwritten/mpmd_two_core_add/front.sh
host/mpmd_two_core_add.{hpp,cpp}  3 grids (full, head, tail), 6 kernel objects
test/main.cpp                  bf16-clean A/B; CPU reference
```

## Topology

```
                  m_grid_full = (0,0)..(0,1)         used by pipes & sems
                  m_grid_head = (0,0)                used by head's 3 kernels
                  m_grid_tail = (0,1)                used by tail's 3 kernels

DRAM ga, gb ──► (0,0) head ──pa,pb (NOC mcast)──► (0,1) tail ──► DRAM gc
                head_writer + head_math            tail_reader + tail_math
                + head_reader (idle)               + tail_writer
```

## Why pipes/semaphores live on the union grid

`pipe.write_mcast` requires **identical L1 layout** at the destination —
the producer's CB allocation offset on its own L1 is used as both the
source pointer and the remote destination address. If pa/pb were declared
on `m_grid_head` only, tail's L1 wouldn't have a slot for them.

By declaring pa/pb/pc on `m_grid_full`, both cores allocate the same
CB at the same offset. Sub-grid kernels can still reference these pipes
in their args; the runtime just resolves the cb_id, which is grid-scoped
but allocated per-core inside the underlying CoreRange.

Semaphores work the same way: sem_credit / sem_data each get a per-core
L1 slot at the same address on both cores, so `sem.inc(remote_x, remote_y, 1)`
reaches a known address.

## Kernel signatures

Each kernel takes only the args it actually uses — no dummy "core_id" or
unused globals:

**head_reader** — `void kernel()` (no args)

**head_writer:**
```
kernel(global<T> ga, global<T> gb,
       pipe<T> pa, pipe<T> pb,
       semaphore sem_credit, semaphore sem_data,
       uint32 ga_pos, uint32 gb_pos,
       uint32 cons_x, uint32 cons_y,
       uint32 num_blocks, uint32 block_tiles)
```

**head_math:**
```
kernel(pipe<T> pa, pipe<T> pb,
       uint32 num_blocks, uint32 block_tiles)
```

**tail_reader:**
```
kernel(pipe<T> pa, pipe<T> pb,
       semaphore sem_credit, semaphore sem_data,
       uint32 prod_x, uint32 prod_y,
       uint32 num_blocks, uint32 block_tiles)
```

**tail_writer:**
```
kernel(global<T> gc, pipe<T> pc,
       uint32 gc_pos,
       uint32 num_blocks, uint32 block_tiles)
```

**tail_math:**
```
kernel(pipe<T> pa, pipe<T> pb, pipe<T> pc,
       uint32 num_blocks, uint32 block_tiles)
```

## Compared with two_core_add

| aspect             | two_core_add                  | mpmd_two_core_add              |
|--------------------|-------------------------------|--------------------------------|
| device source files| 3 (reader, writer, math)      | 6 (head_+tail_ × r/w/m)        |
| kernel binaries    | 3 — runtime branched          | 6 — distinct                   |
| host kernel objs   | 3                             | 6                              |
| host Grid objs     | 1                             | 3 (full + head + tail)         |
| set_args calls     | 6 (3 kernels × 2 cores)       | 6 (1 per kernel)               |
| code path overhead | every core has every branch   | each core has only its branch  |
| DSL backend fit    | hard — every core same ISA stream | natural — 1 spec → 1 kernel |

## Trade-off: which style for what?

- **SPMD-via-core_id**: nice when most cores are doing similar work (e.g.,
  N-way data parallel). One source file, one binary, smaller compile time.
- **True MPMD (multi-Grid)**: nice when cores do *qualitatively* different
  jobs (DRAM-fetch vs forward vs compute). Each kernel has only the args
  it needs; no "dead branches"; codegen-friendly.

Phase 3's DSL surface should generate **MPMD style** by default — one
"spec" per pipeline stage compiles to one kernel binary, no branching.
