# two_core_add (phase 2 step 1)

`C = A + B` over 4 tiles of bfloat16, split across 2 cores:

- core (0,0) head: reads A, B from DRAM and NOC-mcasts to (0,1)
- core (0,1) tail: receives A, B over NOC; computes `C = A + B`; writes C to DRAM

Both cores run the same Tanto kernel binaries (one reader, one writer, one
math). Roles are selected by a `core_id` runtime arg. This is the MPMD-via-
parameterization pattern that the rest of phase 2 builds on.

## Kernel signatures (runtime args)

When editing host or kernel: these signatures are **position-checked, not
name-checked**. Drift between them is the most common bug.

**reader:**
```
kernel(pipe<T> pa, pipe<T> pb,
       semaphore sem_credit, semaphore sem_data,
       uint32 prod_x, uint32 prod_y,
       uint32 num_blocks, uint32 block_tiles,
       uint32 core_id)
```

**writer:**
```
kernel(global<T> ga, global<T> gb, global<T> gc,
       pipe<T> pa, pipe<T> pb, pipe<T> pc,
       semaphore sem_credit, semaphore sem_data,
       uint32 ga_pos, uint32 gb_pos, uint32 gc_pos,
       uint32 cons_x, uint32 cons_y,
       uint32 num_blocks, uint32 block_tiles,
       uint32 core_id)
```

**math:**
```
kernel(pipe<T> pa, pipe<T> pb, pipe<T> pc,
       uint32 num_blocks, uint32 block_tiles,
       uint32 core_id)
```

## Per-core role branches

| core_id | logical core | reader              | math                | writer                  |
|---------|--------------|---------------------|---------------------|-------------------------|
| 0       | (0,0) head   | no-op               | drain pa, pb        | DRAM read → mcast → push |
| 1       | (0,1) tail   | wait+credit+receive | compute pa+pb → pc  | drain pc → DRAM         |

Why head's reader is a no-op and head's writer does everything: see
`doc/notes.md` "Cross-core pipe protocol".

Why head's math drains pa, pb: writer pushes them every iteration but no one
else pops on head; without the drain, after `depth` iterations the writer's
`reserve_back` deadlocks.

## Pipes & semaphores

```
m_pa, m_pb : INPUT,  depth=2, frame_size=1   cross-core 0→1
m_pc       : OUTPUT, depth=2, frame_size=1   used only on tail
m_sem_credit : tail increments → head waits  (consumer credit)
m_sem_data   : head increments → tail waits  (data ready)
```

All declared on the 1×2 grid `(0,0)..(0,1)`. L1 layout is identical on both
cores; the cross-core mcast lands at the same offset on the consumer's L1.

## Per-iteration handshake (head ↔ tail)

```
HEAD WRITER (BRISC)              TAIL READER (NCRISC)
pa.reserve_back                  pa.reserve_back
pb.reserve_back                  pb.reserve_back
pa.read(ga); pb.read(gb)         sem_credit.inc(head)
read_barrier
sem_credit.wait(1); set(0)       sem_data.wait(1); set(0)
pa.write_mcast → tail            (data arrives)
pb.write_mcast → tail
write_barrier
sem_data.inc(tail, 1)
pa.push_back; pb.push_back       pa.push_back; pb.push_back
```

Order matters: consumer reserves+credits **before** producer mcasts. If
producer races ahead, it overwrites a frame the consumer is still draining.
